Teste Técnico — Dev Frontend (Next.js / React)

Prazo: 3 dias úteis a partir do recebimento.
Entrega: link do repositório público no GitHub.
Diferencial: Link de deploy (Vercel/Netlify).

Contexto: O NEO é a plataforma de monitoramento e gestão operacional da Estech. Ele monitora equipamentos (refrigeração, energia, ar-condicionado) em tempo real, gera chamados automáticos quando detecta anomalias e fornece dashboards para operação e gestão. Seu teste simula um módulo real dessa plataforma.

Parte 1 — Projeto prático (70% da nota)

Construir um módulo "Chamados" com duas visões, usando os dados mock fornecidos abaixo.

Stack obrigatória

  • Next.js 14+ (App Router)
  • TypeScript (tipagem estrita, sem any)
  • Ant Design (biblioteca de componentes base)
  • React Query (TanStack Query) para gerenciar dados assíncronos

Requisitos

  1. obrigatório Identidade Visual: Use o ConfigProvider do Ant Design para customizar a cor primária (Primary Color) para o laranja da marca: #ec6725.
  2. obrigatório Lista de chamados: tabela com paginação server-side (simule com os mock data), filtros por status, prioridade e área, busca textual por título e ordenação por data de abertura e prioridade.
  3. obrigatório Volume: a lista deve lidar com 1.000+ itens sem travar a UI. Gere os dados extras programaticamente (dica: use @faker-js/faker). Descreva no README a estratégia adotada (virtualização, paginação, lazy loading, etc.).
  4. obrigatório Drawer de detalhe: ao clicar em um chamado, abre um drawer lateral com todas as informações do item + timeline de atualizações.
  5. obrigatório Formulário "Novo chamado": modal ou página com campos (título, área, prioridade, descrição, equipamento). Validação com React Hook Form + Zod. Ao submeter, o novo chamado aparece na lista.
  6. obrigatório Duas visões (toggle):
    • Técnico — foco na lista de chamados e ações operacionais.
    • Gestor — foco em indicadores: chamados por área, por status, tempo médio aberto. Pelo menos 1 gráfico (Recharts, Chart.js ou equivalente).
  7. obrigatório Estados: loading skeleton, empty state, error com botão de retry.
  8. obrigatório Componentes reutilizáveis: no mínimo 3 componentes extraídos e reutilizados (ex: StatusBadge, PriorityTag, DataTable, DrawerDetail, StatCard).
  9. obrigatório README: curto e objetivo —
    • Como rodar o projeto
    • 2 decisões de arquitetura/UX justificadas
    • O que você faria diferente com mais tempo
  10. bônus Deploy: disponibilizar um link do projeto rodando (Vercel, Netlify, etc.).
  11. bônus Testes: pelo menos 1 teste unitário (Jest/Vitest) e 1 teste e2e (Cypress/Playwright) cobrindo filtro ou ordenação.
  12. bônus Responsividade: funciona bem em tela de celular (técnico em campo).
Dica: Não precisa de backend real. Simule as chamadas com funções assíncronas (async/await + setTimeout) encapsuladas em hooks do React Query. Para gerar o volume de 1.000+ itens, recomendamos bibliotecas como @faker-js/faker.

Parte 2 — Perguntas conceituais (30% da nota)

Responda no próprio README do projeto, na seção "Respostas conceituais". Seja direto — 5 a 10 linhas por resposta.

  1. Cache e mutação: Você tem a lista de chamados carregada via React Query com filtros ativos (status = "Aberto", área = "Refrigeração"). O usuário cria um novo chamado pelo formulário. Como você garante que a lista reflita o novo item imediatamente, sem refetch completo de todos os filtros? Descreva sua estratégia (optimistic update, invalidação seletiva, ou outra).
  2. Performance: Uma tabela de equipamentos com 5.000 linhas e 15 colunas está demorando 3 segundos para renderizar e trava ao filtrar. O usuário é um técnico de campo usando celular Android médio. Descreva, em ordem de prioridade, as abordagens que você aplicaria para resolver.
  3. Arquitetura de componentes: Você criou um <StatusBadge /> usado em 4 telas diferentes. Em uma tela ele precisa exibir um tooltip, em outra precisa abrir um dropdown ao clicar, e em uma terceira é apenas visual. Como você projeta esse componente para ser reutilizável sem virar um "mega-componente" cheio de props condicionais?

Importante: Valorizamos código que parece escrito por um humano que entende o problema, não por um prompt genérico. Se usar IA como ferramenta, use-a bem — queremos ver suas decisões de arquitetura e UX, não output padrão.
